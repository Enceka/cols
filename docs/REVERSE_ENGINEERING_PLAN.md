# CODOL 3.3.3.3：Rust 服务端重建计划

日期：2026-10-06。状态：认证、协议 210、公共配置、文件及公共档案真实上传/重登已验证。空测试目录初始化完成，客户端停在无忙碌弹窗的新玩家引导；非空背包、私有档案与完整大厅仍未恢复。最新进展见 [ONBOARDING_PROGRESS.md](ONBOARDING_PROGRESS.md)，传输与认证见 [AUTH_LOBBY_PROGRESS.md](AUTH_LOBBY_PROGRESS.md)。

用户最新确定的优先级：第一阶段先恢复登录、背包和大厅；双客户端、一张地图、一种模式的最小联机对局调整为第二阶段。优先使用 GameHub 的 Mac 兼容层，Parallels 作为对照环境。

新增参考：用户提供 CODOL-AlphaBuild（主要针对 1.1.1.13）。优先采用其认证票据、Tiger/3DES、大厅编码和背包/档案研究，按 3.3.3.3 的已观测 HTTPS JSON 协议及资源定义适配。逐项结论见 [ALPHA_BUILD_REVIEW.md](ALPHA_BUILD_REVIEW.md)。当前目标版本保持 3.3.3.3。

后续验证已确认版本差异：票据核心可以沿用，目标大厅本身要求协议 210 与 AES/HMAC 通道，不能直接使用参考旧版的 3DES 大厅外层。

工程路线为：固定客户端样本 → 验证 Mac 运行环境与启动链 → 恢复登录及会话协议 → 档案/背包/大厅闭环 → 房间与对局分配 → 单客户端进图 → Rust 权威对战 → 双客户端验收。每一步均留下可复现证据。现有材料足以开始逆向调查，尚不足以承诺完整复刻的工期。

本轮检查依据及文件指纹见 [CLIENT_BASELINE.md](CLIENT_BASELINE.md)。本计划中的架构和验收标准是设计目标；带有“候选”“待验证”的内容还不是已恢复的协议事实。

**目标与完成标准**

第一阶段的可交付版本由真实客户端连接 Rust 服务端，以本地测试身份完成登录，进入可交互的大厅，读取和操作一组有效的背包物品，并在重启后恢复数据。具体请求次序以客户端实际调用链为准，大厅初始化所必需的档案和背包数据可先于界面出现。

第一阶段范围：

- 登录：恢复客户端必需的启动参数、握手、会话及认证响应；使用本地测试账号，不把恢复真实 QQ 登录作为前置条件。
- 档案：提供客户端初始化必需的玩家标识、名称及经验证的基础字段，区分新建与已有档案。
- 背包：从本地数据确认少量真实物品 ID、分类、资源关联和装备槽位；恢复列表展示、查看、装备/卸下或客户端实际支持的对应操作。
- 持久化：分离物品定义、玩家持有实例和装备配置；服务端验证归属、槽位约束及修改结果，重复请求不产生重复物品，重启后保留状态。
- 大厅：正常完成加载、维持连接、进入背包并返回，处理注销及重新登录。先覆盖这些界面真正需要的任务；房间、匹配和开局在第二阶段实现，除非大厅初始化明确依赖其最小响应。

第一阶段验收包括两个测试身份的数据隔离，但不要求两个玩家开始对战。单纯跳过错误弹窗、显示静态菜单或全部返回空成功，不算恢复上述功能。

第二阶段由两个独立身份连接同一服务端，在一张资源完整的地图中完成固定规则的对局。优先选择规则简单的死亡竞赛类模式，具体模式 ID、地图 ID 和武器 ID 由本版本数据验证后确定。最小功能包括建房/加入、进图、出生、移动、观察另一玩家、一种武器、伤害、死亡、重生、计分、结束及离开对局。

实时状态由 Rust 服务端持有并验证。仅进入菜单、打开地图、回放一段数据或转发两个客户端的报文，均不满足“双客户端最小联机对局”的完成标准。

完整武器库、PVE/AI、商城、活动、排行榜、公网匹配和复杂 NAT 穿透留到后续阶段。最初支持固定版本及本机/局域网部署。

**已知基础与关键未知**

| 项目 | 目前证据 | 对计划的影响 |
| --- | --- | --- |
| 版本 | IIPSVersion.ini 为 3.3.3.3，资源清单指向 Experience/V3.3.3.3 | 用可执行文件 SHA-256 固定具体样本；不只依赖文件夹或安装包名称 |
| 客户端 | 主程序为 Windows x86 PE32，导入 d3d9.dll | Mac 上需验证 32 位 Windows 程序及 Direct3D 9 的兼容性 |
| 启动器 | 离线启动器是 .NET 程序，存在主程序、IIPS、CrossProxy 等字符串 | 优先反编译启动器，恢复真实启动链与参数传递 |
| 登录/大厅候选 | 主程序含 dwauth.ini、bdByteBuffer、bdLobbyEventHandler 等字符串 | 优先寻找配置读取、序列化、认证和大厅任务分发的交叉引用 |
| 对战候选 | 含 getchallenge、challengeResponse、connectResponse 等字符串 | 追踪连接状态机、报文解析和快照应用路径；不能据此直接套用其他 COD 协议 |
| 资源 | 362 个 .ifs 文件与本地清单文件名逐一匹配 | 具备资源分析起点；仍需验证块完整性、索引和地图实际加载 |
| 参考样本 | 未找到 PDB、pcap/pcapng 或服务端源代码 | 客户端反序列化函数和状态变化是主要依据，不能依赖不存在的官方响应抓包 |
| 环境 | 当前为 macOS arm64，有 Rust 工具路径和 Parallels 应用 | Mac 承担开发及原生服务端；兼容层与虚拟机承担客户端实验 |

主程序的普通 PE 节布局及可读字符串，不足以证明不存在保护机制。目录中的 TerSafe/TenProtect 文件，也不足以证明当前启动路径一定加载它们。两者均由加载模块和运行轨迹确认。

**Mac 优先的运行策略**

Rust 服务端目标为原生 `aarch64-apple-darwin`，后续保留 Windows/Linux 构建能力。客户端沿用现有 Windows x86 程序；“通过 Mac 运行”在本计划中指兼容层运行客户端，而非重写整个游戏客户端。

当前已选择本机 GameHub 的 wine-proton_10.0，在项目独立 prefix 与客户端克隆中实测到 HTTPS AUTH 请求。继续沿此路线调试，图形/声音与完整大厅仍须分别验收。CrossOver 可作为未来的其他运行选择，其工具能力不替代 CODOL 实测。[CrossOver 使用指南](https://support.codeweavers.com/cn_CN/user-guides/crossover-mac-user-guide)

按以下顺序验证：

1. 反编译启动器，记录工作目录、命令行、子进程、环境变量、配置与 IPC 依赖，识别必需组件。
2. 在独立环境中启动游戏，确认 PE 加载、运行库、Direct3D 9、声音、输入和 IIPS 初始化；图形后端以实测选择。
3. 即使远端服务不可用，也要确认进程能稳定进入连接尝试，并获得可重复的错误及网络记录。此时不要求先进入大厅或地图。
4. 第一阶段先验证一个客户端登录、背包与大厅的稳定性，再以两个身份验证数据隔离。第二阶段为双客户端分离配置、日志及可写缓存，排查单实例锁和端口冲突，继续验证进图及双开稳定性。
5. 记录 macOS、兼容层版本、容器配置、运行库及每次实验差异，保留可重建的运行说明。

为初次 Mac 兼容性实验预留约 1–2 个工作日，这是调查时间盒。若一直无法到达稳定的联网阶段，先用已安装的 Parallels 建立比较环境，再定位兼容层差异。Apple Silicon 上通常使用 Windows 11 Arm，x86 应用通过 Windows 仿真运行；这与真正的 Windows x64 调试环境不同，调试器和模块兼容性仍需验证。[Parallels 官方说明](https://kb.parallels.com/us/125375)、[Microsoft 仿真说明](https://learn.microsoft.com/en-us/windows/arm/apps-on-arm-x86-emulation)

若两条路线都无法提供可靠的 x86 动态观测，再使用真正的 Windows x64 机器作为调试基准。即使客户端暂时在虚拟机或另一台机器中运行，Rust 服务端仍放在 Mac 上；来宾访问服务时使用实际可达的宿主机地址。

**逆向工作的顺序**

1. 固定样本。保留原始客户端，后续运行使用工作副本。建立主程序、关键 DLL、配置及大厅所需资源的哈希清单；记录工具版本和修改差异。补齐安装包校验和首批资源块校验，选定地图的校验进入第二阶段。
2. 恢复启动链。用 ILSpy 分析 .NET 启动器，用 Ghidra 分析原生主程序。确认启动器字符串对应的分支是否真的执行；特别核实缺失的 `codoMP_client_shipRetailBase.dll` 是必需依赖还是可选分支。按观察到的启动行为设计可重复的研究启动方式。[ILSpy](https://github.com/icsharpcode/ILSpy)、[Ghidra](https://github.com/NationalSecurityAgency/ghidra)
3. 建立端点与状态图。追踪 `dwauth.ini`、`stun.ini`、地址解析及 socket 调用，列出认证、大厅、资源服务和对战端点。优先使用实际存在的配置入口连接本地服务；若必须修改客户端，补丁按样本哈希匹配，限定到明确功能并支持撤销。
4. 分清传输层。分别记录 TCP/UDP、长度字段、字节序、消息类型、连接生命周期、心跳、重试和错误路径。关联客户端动作、网络字节和解析函数，避免把资源下载流量或 NAT 探测当作游戏业务。
5. 恢复会话及序列化。定位认证结果的读取、会话密钥使用、任务结果解析和字段校验。加密算法、压缩、填充、校验、类型标签及长度单位均由调用关系和实验确定。Rust 发出的响应由客户端真实解析并推进状态后才算验证通过。
6. 完成第一阶段业务。沿客户端请求顺序，实现本地测试身份、档案、背包读取、装备修改、持久化及大厅初始化/心跳。区分传输成功、业务成功和最终界面状态。对未知请求保存上下文并明确标记；每种响应都满足已知字段及状态约束。
7. 第一阶段通过后，恢复房间、对局分配及实时协议。追踪 challenge/connect、可靠命令、序号、确认、分片、用户输入、初始世界状态、实体快照、增量压缩和断线处理。最终线格式必须逐字段符合本版本，不能用自定义 JSON 或其他游戏的实现替代。
8. 第二阶段恢复最小对战规则。提取所选地图的碰撞、出生点、必要实体及一种武器的数据；实现客户端期望的移动、射击事件、伤害、死亡、重生与计分。验证是否需要脚本执行；仅支持最小模式需要的脚本/规则及引擎接口。

TCLS/Cross 目录里的 TDR 文件先做归属识别，不能预设它们描述了主游戏协议。公开 CODOL 研究记录可用于提出 AUTH/LSG/STUN 等调查方向，但其样本版本和作者猜测必须与本地证据区分。[研究作者记录](https://github.com/zzVertigo/CodOnline-Disected)

资源处理先分析 IIPS 索引及读取接口，优先定位 common/marketplace 等候选容器中的界面、物品定义和配置，并用调用关系确认实际归属。物品 ID 不按名称猜测。第二阶段再验证所选地图的碰撞及规则数据，决定使用离线转换工具或 Rust 解析器。客户端仍使用自己的显示资源。资源文件存在不等于全部块已缓存，也不等于其中包含完整的原服务端逻辑。

第二阶段开始前检查本版本是否残留可运行的本地对战或主机逻辑。如果存在，可作为观察行为、生成样本及比较结果的实验工具。项目交付仍以 Rust 实现服务端为准；若对战依赖原游戏进程执行，只能记为过渡验证成果。

**Rust 实现结构**

初期使用一个 Cargo workspace、一个服务进程和明确的模块边界。按协议发现结果启用对应监听器，端口在配置中定义。下面的划分是实现建议，不表示原游戏服务端采用相同结构。

| 模块 | 职责 | 主要验证方法 |
| --- | --- | --- |
| protocol | 字节/位读取、帧边界、字段类型、版本配置、加解密适配 | 已观测样本逐字段及逐字节比对 |
| transport | TCP/UDP I/O、会话路由、分片重组、超时与背压 | 分包/合包、乱序、重传、失联场景 |
| backend | 第一阶段认证、档案、物品目录、背包、装备及大厅；第二阶段房间和对局票据 | 实际界面操作和客户端状态推进 |
| game | 第二阶段固定步长模拟、玩家及实体状态、移动碰撞、武器、计分、快照 | 双客户端一致性及可重复输入场景 |
| assets | 第一阶段提取必要物品/界面数据；第二阶段地图适配 | 客户端能显示正确物品，后续再验证地图及碰撞 |
| storage | 本地账号、物品实例、装备槽位、必要档案和配置 | 重启恢复、请求幂等及身份隔离 |
| diagnostics | 结构化日志、状态转换、原始字节和解析结果关联、回放 | 每个协议结论能追溯到样本及实验 |

网络 I/O 建议使用 Tokio，缓冲区使用 `bytes`，配置和内部记录使用 Serde/TOML，日志使用 `tracing`。Tokio 提供异步网络运行基础；对战模拟安排独立的固定步长执行循环，通过有界队列和网络层交换数据。[Tokio 官方教程](https://tokio.rs/tokio/tutorial)

持久化先使用 SQLite。密码算法和相应 Rust 依赖在协议确认后选择，不预设 AES、3DES、RSA 或其他具体方案。Serde 等内部序列化工具不能自动生成游戏要求的线格式。第一阶段实现 protocol、backend、storage 和 diagnostics 的最小闭环，game 模块随第二阶段引入。

服务器运行于 64 位 macOS，客户端运行于 Windows x86，两者交换的是已定义的网络字节。明确处理整数宽度、浮点表示、位字段、字节序和字符串编码，禁止把 Rust 内存结构直接视为客户端结构。Tick、快照发送率及超时参数由客户端行为确定，并记录依据。

仓库逐步形成以下目录；当前已创建 protocol/server 两个 crate 及工具、配置、指纹和文档，业务、数据库及实时模拟模块随证据形成后接入：

```text
server/
  docs/                规划、证据、协议及状态机说明
  crates/protocol/     无网络依赖的编解码核心
  crates/server/       当前为配置和网络观测；后续加入业务、模拟与存储
  tools/               静态提取、资源转换、样本回放工具
  fixtures/            最小协议样本及预期解析结果
  configs/             本机/局域网实验配置
  captures/            本地实验记录，不纳入常规版本控制
```

**里程碑及验收门槛**

| 阶段 | 主要产物 | 通过条件 |
| --- | --- | --- |
| M0：样本与环境 | 哈希基线、启动链说明、Mac 兼容性记录、首批资源读取报告 | 至少一种环境可重复启动到联网尝试；能区分环境错误和协议错误 |
| M1：本地登录 | 端点图、协议规格、Rust 网络闭环、认证及会话 | 真客户端连接本地服务并接受认证结果，推进到档案/大厅初始化；不能只看连接是否建立 |
| M2：档案与背包 | 有效物品目录、持有实例、装备操作、SQLite 持久化 | 客户端可显示少量真实物品，完成一次装备变更；重新登录及重启服务后保持状态，两个身份互不串数据 |
| M3：第一阶段交付 | 大厅初始化、心跳、退出/重登、运行说明和回归样本 | 真实客户端可登录→大厅→背包修改→返回大厅→退出→重登；连续驻留 30 分钟并重复三次完整操作流程，无崩溃、串号或卡死 |
| M4：房间与单客户端进图 | 房间、对局分配、资源路径、连接状态机、初始世界状态 | 客户端完成进图和出生；持续接受 Rust 服务端状态，无持续解析错误或超时 |
| M5：双客户端最小对局 | Rust 移动/碰撞、快照、射击伤害、死亡重生、计分及结束 | 两端能互相观察和交战，服务器状态一致；完整跑完并重复开启对局 |
| M6：第二阶段交付 | 对局运行说明、回归样本、稳定性报告 | 新工作副本能按文档重现；连续运行 30 分钟，三次对局循环无崩溃、串号或卡死 |

第一阶段的高风险门槛是 M1 的会话/认证和 M2 的有效业务数据：需要知道客户端为什么接受响应，以及物品和档案字段来自哪里。若界面仍被后续依赖阻塞，记录最后一个已验证状态和下一条请求。

第二阶段的 M4 是另一高风险门槛：若无法恢复世界状态、快照字段或地图必要数据，先形成缺口报告和实验路线，再扩展游戏业务。M5 必须得到服务端权威状态的证据；纯转发或客户端各算各的状态不能通过。

Mac 运行体验单独验收：第一阶段要求至少一个客户端通过 Mac 兼容层稳定完成登录/背包/大厅流程；第二阶段继续验证双开和对局。若只有虚拟机路线通过，明确记录对应功能已通过、Mac 兼容层运行仍未完成。

**证据与测试规则**

每个消息定义记录：样本 SHA-256、传输方向、触发动作、连接状态、报文偏移/长度、字段编码、相关函数 RVA、预期响应、错误结果和置信度。置信度分为已观测、实验验证、推断和未知。跨样本地址用 RVA 加哈希识别；文件偏移、RVA 和运行时地址分别记录。

优先构建三类验证：真实客户端输入/解析结果作为编解码依据；连接及业务状态迁移作为集成验证；实际大厅/背包操作和后续双客户端对局作为验收。编码器和解码器互相 round-trip 只能作为补充，不能独立证明协议正确。

有了网络核心后，再加入针对性的边界测试：截断、超长长度、未知任务、重复报文、TCP 合包/拆包、UDP 丢失/乱序、序号回绕及连接退出。对外部输入解析做有界分配与模糊测试；对已经验证的正常流程保留固定回归样本。

第一阶段重点测试新档案与已有档案、背包读取、有效装备变更、无效物品/槽位请求、重复请求、断线/重登和服务重启。记录客户端显示值、协议响应和数据库状态，验证三者一致。

第二阶段对局测试至少覆盖站立、移动、跳跃、贴墙、出生点、命中/未命中、死亡重生和结束。延迟补偿以观测到的机制为准；先完成低延迟局域网，再使用受控延迟/丢包检验协议行为。涉及身份、会话与对局的数据需关联追踪，避免两个测试客户端共用状态造成假成功。

**工期与首轮任务**

首轮安排约 5–10 个工作日的可行性调查，具体取决于可用运行环境和工具。这是评估窗口，不是第一阶段完成期限。调查输出应能回答：客户端能否在 Mac 上稳定启动、启动器实际做了什么、如何进入本地连接、认证响应如何解析、大厅依赖哪些任务、物品/档案数据可以从哪里恢复。

第一阶段在 M1 通过后，依据实际发现的大厅任务和背包字段重新估算 M2/M3。第二阶段的完整纯 Rust 对战服务按月级研究项目评估；缺失服务器逻辑、碰撞数据、脚本支持及客户端保护都可能增加范围，进入 M4 前单独评估。

执行顺序：补齐样本清单 → 反编译离线启动器 → 追踪 `dwauth.ini` 及网络入口 → Mac 启动实验 → 采集连接与状态变化 → 固定首条协议规格和验证样本 → 创建最小 Rust 网络闭环 → 沿实际调用链恢复档案、背包和大厅。第二阶段线索保留在发现文档中，当前资源分析以启动、大厅及物品数据为重点。
