# 玩家角色外观与首次资源发布

2026-10-11，3.3.3.3原客户端、纯Rust后端。

过去玩家在对局、尸体与前三名使用固定默认男性：model4及部件3/2/5/6。现在从已校验公共档案的当前角色槽读取角色包和换装，用本版资源选出身体部件，并按本图空闲模型编号注册。当前角色792实际组成为INFbaseE身体/衣服、INFbaseA鞋/手套、Hernandez头部/头饰，非原来的socomb默认头。

## 资源和身份链

- `characterClasses[0..11].slots[0..8]`与`currentCharacterIndex`使用当前v233定义的真实偏移；9个槽不是固定连续数组。偏移证据在 `fixtures/protocol/character-slots-3.3.3.3.json`。
- `tools/client_state.py --outfits`只读市场物品及保留的角色缓存。角色原始StringTable可能已卸载，不能把空表当成无角色资源。
- 物品解析为 `0x5845b0` 的40字节记录；角色包detail池 `0x02dbba44`、步长40。包+2性别、+3肤色（0wht/1cau/2yel/3blk）、+8起12个默认物品，+32/+36成员列表。`0x569cba..0x569d3b`独立验证性别/肤色消费者。
- 变体缓存由 `0x40d320`创建：`0x17e02e4`分组范围、`0x17cd290`步长16，+0部件索引、+4选择掩码、+8模型名、+12第一人称模型名。部件名通过本版小写乘/XOR哈希映射到分组索引，不把市场ID直接作为变体号。
- `0x40c980/0x40c800`选择第一个包含性别/阵营/肤色全部请求位的变体；shared记录包含多个位。未匹配的可选帽子/背心保持空，必需身体部件缺失则拒绝。角色612的TF头饰正是可选无匹配的实际例子。
- `prepare_player_appearance.py`生成独立目录，保留两个来源SHA和本版身份；当前27个角色包、940个可穿戴物品。运行时校验自选角色/换装所有权、允许成员及同类型冲突；包自带部件不要求作为单独购买项。
- 玩家外观在本局冻结。换背包和保存名片不会重用模型槽改变当前尸体、回放或人物身份；新角色在下一局重新解析。第一人称手臂仍沿原武器准备路径，本轮只实现第三人称身体，不宣称手臂也已全部按换装更新。

## 初始模型名单与压缩消息

用户指出Bot开局先显示统一默认人物。此前模型名字为进图后的可靠`d`命令，原因是完整gamestate超出单包上限。现在模型名单进入初始gamestate；大消息使用原生zlib标志：ACK最高位置1，先压缩正文再XOR；客户端 `0x467520 →0x46bf80 →0x46e6a0 →0x659040`反向处理，展开上限128KiB。小包保持原字节；压缩后仍超过本版1154阈值则明确拒绝，不冒充已实现分片。

三图当前完整角色快照930字节；gamestate为1960/1978/1979字节，含头压缩包721/726/733字节。重复配装在独立`for_profile`准备路径中也按实际武器注册表去重，避免重复configstring。

提前发布名字**未完全解决Bot冷加载回退**。连续只读采样 `client-1791676989253/appearance-load-1791677061810.json` 覆盖状态0→3→5→6→7→8→9→10，首个可玩时间1000ms：玩家client0已是完整自选六部件；部分Bot仍用客户端备用人物，各自最后一次不匹配在2633..4212ms。其后全部变为各自角色，说明还有客户端按角色异步装载的过程。不能把当前1.6..3.2秒回退说成官方完整服务端的必然开局设计，也不能把提前发送算成问题彻底修复。
